# 年度写作分支方案

## 通俗解释：日常写作会怎样变化

目前不同项目分散在多个分支和目录中，找材料时需要先记住项目对应哪个分支。建议把一个申报年度的项目放进同一个年度工作目录，例如进入 `ChineseResearchLaTeX.worktrees/writing-2027/` 后，就能撰写 2027 年的多个申请。

可以把它理解为每年一本工作册：年度分支保存这本工作册的修改历史，worktree 是电脑上打开它的独立目录，`projects/` 中的各个项目是工作册里的不同材料。多个年度目录可以同时存在。

例如，现在 2026 年教育项目和其他课题分别使用项目分支；采用方案后，同一年度的项目集中到 `writing/2026`，提前准备的 2027 年申请放到 `writing/2027`。年度按申报年份确定，因此可以在 2026 年提前建立 2027 年工作目录。

## 当前情况与判断

本次只读检查确认：

- 当前目录使用 `main`，仓库登记了 8 个 worktree，尚无 `writing/<年度>` 分支。
- 已有分支混合使用项目名、年度和开发任务命名。
- `main` 工作目录中存在已暂存、未暂存和未跟踪内容，涉及正文、公共包、脚本和说明文档。
- 当前 `projects/` 中同时存在 2026 年与 2027 年项目。
- 新项目创建与 VS Code 配置依赖现有项目目录规则，应保持 `projects/<项目名>/` 这一层级。

因此，首次采用年度分支需要迁移现有材料。仅从 `main` 创建 worktree，会获得该分支已经提交的内容；当前未提交和未跟踪的文件不会自动进入新目录。

## 目标与分支规则

| 分支 | 用途 | 建立方式 |
|---|---|---|
| `main` | 长期维护公共包、模板、脚本和 Skills | 保持模板主线职责 |
| `dev` 或已有修复分支 | 开发、验证公共模板改动 | 沿用现有开发流程 |
| `writing/2026` | 2026 申报年度的项目写作 | 从选定且验证过的 `main` 提交创建 |
| `writing/2027` | 2027 申报年度的项目写作 | 从该年度开始时验证过的 `main` 提交创建 |
| `writing/2028` | 后续年度项目写作 | 延续相同规则 |

年度内的多个项目通过目录区分，日常写作使用该年度的一个长期分支。已有项目分支作为迁移来源保留。

每个年度分支都拥有完整仓库结构，包括公共包、脚本和模板示例。分支名称不会自动筛选文件年份；当年项目通过命名和年度项目清单识别。

## 工作目录与项目组织

沿用当前仓库已有的 sibling worktree 路径：

```text
/home/yanfeng/fund-writing/
├── ChineseResearchLaTeX/                    # main：模板和工具维护
├── ChineseResearchLaTeX-dev/                # 已有开发工作目录
└── ChineseResearchLaTeX.worktrees/
    ├── writing-2026/                       # writing/2026
    ├── writing-2027/                       # writing/2027
    └── writing-2028/                       # writing/2028
```

年度工作目录中的项目保持现有布局，例如：

```text
writing-2027/
├── packages/
├── scripts/
├── skills/
├── docs/
└── projects/
    ├── NSFC_General_Clean/                  # 可用模板
    ├── NSFC_Local_Clean/                    # 可用模板
    ├── NSFC_2027_Mapping/                   # 当年项目
    └── NSFC_2027_yuwei_llm/                 # 当年项目
```

保留 `projects/NSFC_<年度>_<主题>/` 命名，开放基金等项目继续使用其已有 `build_profile`。项目根目录继续维护同名 `.code-workspace`、`.vscode/` 和适用的 `template.json`，缓存仍隔离到 `.latex-cache/`。

年度分支内维护一份简短项目清单，记录申报年度、项目路径、申报类别、当前阶段和最终提交版本，便于查找进度。论文等跨年任务按计划提交年份归类，跨年未完成时按项目转入下一年度并注明来源。

## 每年创建与模板同步

每年准备新年度材料时，从已经验证的 `main` 提交创建年度分支。新的年度可以提前建立，创建操作执行一次即可。

新年度默认以当时的模板主线为基础，需要沿用的旧稿选择性复制到新的年度项目目录，再更新项目名、申请年份和工作区配置。这样新年度使用较新的模板，也避免整年累积全部旧项目和试验改动。

写作期间遇到共享样式或脚本问题，在开发分支形成独立、可验证的模板修复提交，再同步到 `main` 和确实需要修复的年度分支。优先选取只包含模板修复的提交；若提交依赖前置改动，需要一并评估并构建验证。年度正文保存在年度分支，默认不整支合并回模板主线。

年度结束后，在最终确认的提交上创建 `archive/writing-2026` 等归档标签，并保留年度分支。标签固定当时的源码版本；年度分支后续如有补正，可以继续提交，归档标签保持原有位置。最终 PDF 与构建工具版本也应留存，便于后续核对版式。

## 首次迁移顺序

1. 盘点 `main` 和已有项目 worktree 的已提交、未提交及未跟踪内容，列出每个项目的申报年度、正文来源和公共包依赖；先保存可恢复的副本。
2. 选择明确的基准提交，创建 `writing/2026` 和 `writing/2027` 及其独立目录。按项目把已提交材料与尚未提交的正文迁入对应目录；共享模板依赖单独整理，避免遗漏当前尚未提交的新 profile、样式和构建器修复。
3. 在年度目录核对内容完整性，检查工作区与元数据，并使用各项目对应的官方构建器验证；分批提交年度正文和模板改动，便于以后选择性同步。
4. 确认迁移可用后，再逐步把 `main` 的日常职责收敛到模板与工具维护。已有分支和目录的清理单独处理。

## 如何确认方案已落地

- `git worktree list` 能列出年度目录与 `writing/<年度>` 分支的对应关系。
- 在各年度目录执行 `git branch --show-current`，得到正确的年度分支。
- 一个年度中的多个项目可以在该目录内直接编辑和提交。
- 修改 2027 年项目时，2026 年目录中的工作文件保持独立。
- 首次迁移的文件核对结果与源材料一致，所有迁入项目通过对应官方构建入口，warning 说明其来源。
- 新年度项目可由现有创建入口初始化，同名 VS Code 工作区和构建配置正确生成。
- 归档标签可定位当年最终源码提交，最终 PDF 和构建环境信息可查。

迁移验证记录和临时产物放在 `tests/` 下的专用子目录。

## 技术补充：年度创建入口

以下命令用于从 `main` 已提交的版本建立年度目录，执行位置是主仓库。首次迁移还需完成上面的材料盘点与复制步骤。

```bash
git worktree add -b writing/2026 ../ChineseResearchLaTeX.worktrees/writing-2026 main
git worktree add -b writing/2027 ../ChineseResearchLaTeX.worktrees/writing-2027 main
```

以后每年替换年度执行同样的创建命令；分支或目标目录已经存在时，进入原目录继续写作。

在年度目录中创建一个 NSFC 项目的现有入口是：

```bash
python3 scripts/create_project.py --template NSFC_General_Clean --name NSFC_2027_Example
```

该脚本会复制模板、过滤缓存和生成的 PDF，并生成项目工作区配置；正文内容与申请信息仍需按新项目调整。开放基金等特殊模板继续按对应 profile 和构建器处理。

在年度目录确认最后提交后，可建立归档标签：

```bash
git tag -a archive/writing-2026 -m "归档2026年度写作"
```

本次交付为方案文档；年度分支创建、材料迁移和归档属于后续实施。
