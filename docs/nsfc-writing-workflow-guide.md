# NSFC 标书 AI 写作工作流指南

本文讲**怎么用本仓库的技能和事实库写一份标书**。

模板安装、编译命令、改哪些 `.tex` 属于另一件事，见 [`docs/nsfc-usage-guide.md`](./nsfc-usage-guide.md)。

---

## 一、先理解三层结构

```text
docs/applicants/<申请人>.md              ← 共用层：跨项目复用的申请人事实
        │                                   身份 / 履历 / 科研项目 / 代表作 / 科研条件
        │ applicant_profile_file（相对路径指向，不复制）
        ▼
projects/<项目>/docs/00_项目事实库.md      ← 项目层：只放本项目特有的事实
        │                                   申报目标 / 研究边界 / 团队 / 数据 / 缺口
        ▼
skills/nsfc-*                             ← 技能层：读上面两层，写 extraTex/*.tex
```

**为什么要分两层**：同一个事实在多份文档各存一份，迟早会打架。真实发生过的例子——A100 八卡在工作条件文档里写着"3 年稳定保障"，在补充问卷里写着"未落实"，AI 读到两种说法只能停下来问你。分层之后申请人事实只有一处，改一次全项目生效。

分层的完整规则、状态口径与隐私要求见 [`docs/applicants/README.md`](./applicants/README.md)。

## 二、开一份新标书：三步

### 第 1 步：建项目

```bash
python3 scripts/create_project.py --template NSFC_General_Clean --name NSFC_你的项目名
```

模板选择：

| 模板 | 适用 | 布局 |
|---|---|---|
| `NSFC_General_Clean` | 面上、青年 | three-part（`1.1` + `2.1`–`2.3` + `3.1`–`3.4`） |
| `NSFC_Local_Clean` | 地区 | five-part（`1.1`–`1.5` + `2.1`–`2.4` + `3.1`–`3.5`） |

> 脚本要求项目名以 `NSFC_` 开头。新项目会自动带上 `docs/` 下的三个骨架文件。

### 第 2 步：确认共用层有你的申请人文件

```bash
ls docs/applicants/
```

没有就新建一份 `docs/applicants/<你的slug>.md`，照 `yan-feng.md` 的结构写：基本身份、教育与工作经历、科研项目（`P-H*` 主持 / `P-V*` 参与）、代表作（`O-*`）、科研条件、跨项目待补事实（`F-GEN-*`）。

**这份文件写一次，以后所有标书复用。** 论文发表了、拿了新项目，只改这一处。

### 第 3 步：填项目事实库 + 接线

编辑 `projects/<你的项目>/docs/00_项目事实库.md`，逐节替换 `<...>` 占位，删掉用不到的小节。

**只写本项目特有的**：申报目标、研究边界、团队名单、数据条件、项目缺口。申请人的履历、论文、科研项目**不要抄进来**。

然后确认 `docs/workflow_status.yaml` 里这几个字段：

```yaml
project:
  type: NSFC_General
  grant_type: 面上项目
  applicant_profile_file: "../../docs/applicants/<你的slug>.md"
  project_fact_file: "docs/00_项目事实库.md"
```

做完这三步，写作流程就不会再问共用层里已经确认过的信息。

首次运行或续跑时，先让状态脚本迁移旧断点并与真实文件对账：

```bash
python3 skills/nsfc-full-pipeline/scripts/pipeline_state.py \
  --project-dir projects/你的项目 migrate --apply
python3 skills/nsfc-full-pipeline/scripts/pipeline_state.py \
  --project-dir projects/你的项目 reconcile --apply
python3 skills/nsfc-full-pipeline/scripts/pipeline_state.py \
  --project-dir projects/你的项目 next
```

这样即使上次在阶段中途退出，也会根据输入/输出指纹恢复；若 `main.tex` 改过，则自动要求重跑布局解析。

## 三、事实的状态口径

事实库里每条都要标状态，AI 按状态决定怎么用：

| 状态 | 含义 | AI 的行为 |
|---|---|---|
| `已确认` | 本人确认过，或有任务书、立项书、出版社元数据等证据 | **直接写入正文，不再询问** |
| `公开来源待终核` | 来自公开主页或既有简历，未逐项终核 | 可作草稿素材，提交前需复核 |
| `待本人确认` | 证据不足 | 不得推断为既成事实 |
| `明确暂无` | 已确认当前不存在 | 可用真实、保守的否定表述 |

**关键**：你回复"无"、"不适用"、"尚未完成"也是**有效的事实决定**，应该记进事实库标成 `明确暂无`。这样同一轮任务不会反复追问同一件事。

需要补充时，AI 应按事实 ID（`F-GEN-*` / `F-项目-*`）**一次性集中问完**，而不是写两段停一次。

## 四、缺信息时：先写下去，回头再补

默认行为是 **`draft_first`** —— 缺事实不停，挖个带编号的坑继续写，你补齐后 AI 按编号回来只改那几句。

### 两种坑，写法不一样

| 缺什么 | 标记 | 说明 |
|---|---|---|
| **可推定**：年度计划月份、预期成果数量口径、实验规模、指标阈值 | `【暂定 …】` | AI 给合理草稿值，正文写完整。不阻塞提交，但会列进最终清单请你确认 |
| **硬事实**：项目批准号、经费额度、论文、获奖、平台型号、团队成员、国基完成情况、各类声明 | `【待补 ID：说明】` | 句子写完整，**只挖掉事实本身**。绝不编造 |

正文里长这样：

```latex
申请人主持国家自然科学基金青年科学基金项目\textbf{【待补 F-GEN-03：批准号与起止年份】}，
围绕功率预测的时序建模开展了工作。
```

用的是普通 `\textbf{}`，没引入新宏 —— Overleaf、独立打包的项目 zip、任意版本的 `bensz-nsfc` 都能编译，标记在 PDF 里肉眼可见。

### 什么时候还是会停

只剩两种。都是"停下来问"比"猜着写"更省事的情形：

- **落点或项目类型解析不出来**（stage 00）—— 不知道该往哪个文件写
- **选题没定**（stage 01）—— 写什么都是编造

研究基础、工作条件、承担项目、各类声明**都不会再挡路**了，它们本来就是填空题。

### 看还欠什么

```bash
python3 skills/nsfc-full-pipeline/scripts/scan_gaps.py --project-dir projects/你的项目
```

输出按事实 ID 分组的位置清单，顺带查两种错：ID 没在事实库里登记、整段只有一个占位（那不是草稿，是伪装成进度的停顿）。加 `--id F-GEN-03` 只看某一条。

### 补齐之后

直接说「我补充了 F-GEN-03」或「补充完了」。AI 会重读事实库找出状态变成 `已确认`/`明确暂无` 的条目，定位后**只改那几句**，不重写整节，然后按改动范围重跑下游检查。

确认为 `明确暂无` 也算补齐 —— 占位换成 `无相关情况。`，不是换成另一个占位。

### 两条要记住的

- **只要还有 `【待补 …】`，这稿就不能提交**。阻塞点没消失，只是从"写作时"挪到了"提交前"
- **缺口清空前，篇幅结论只能算暂定**。挖空稿偏短，补完真实项目和论文常多占 1–2 页；这时候信"还有余量"，补完就得回头再压

正文走完后仍要区分“正文完成”和“整份申请书可提交”：

```bash
python3 skills/nsfc-full-pipeline/scripts/pipeline_state.py \
  --project-dir projects/你的项目 readiness
```

`body_pipeline_ready` 只代表正文 15 阶段与 PDF 通过；`submission_ready` 还要求摘要、申请代码、预算、声明和附件全部完成或明确不适用。

想恢复旧的"缺信息就停"，把断点文件里的 `run.fill_policy` 改成 `blocking`。

## 五、写作顺序与技能选择

### 用编排器跑全流程

```text
请使用 nsfc-full-pipeline 处理 projects/你的项目，从头跑全流程。
```

它按 00–14 共 15 个阶段串联，以 `docs/workflow_status.yaml` 为断点。中断后说「继续」即可续跑，不会推倒重来。

评审后自动改稿：

```text
根据模拟评审报告修复 P0/P1 问题
```

### 或者逐个手动触发

想自己控制节奏就按这个顺序：

| 顺序 | 技能 | 产出 |
|---|---|---|
| 1 | `research-topic-extractor` | 主题与关键词 |
| 2 | `research-literature-review` | 文献综述 + `.bib` |
| 3 | `research-idea` | 科学问题与创新点 |
| 4 | `research-plan` | 研究方案与技术路线 |
| 5 | `nsfc-justification-writer` | 立项依据 |
| 6 | `nsfc-research-content-writer` | 研究内容 + 特色与创新 + 年度计划 |
| 7 | `nsfc-research-foundation-writer` | 研究基础 + 工作条件 |
| 8 | `nsfc-ref-alignment` | 引用一致性核查 |
| 9 | `nsfc-length-aligner` | 篇幅对齐 |
| 10 | `nsfc-humanization` | 去 AI 味 |
| 11 | `nsfc-qc` | 只读质量控制 |
| 12 | `nsfc-reviewers` | 模拟专家评审 |

### 编排器不覆盖的，单独调用

| 环节 | 技能 |
|---|---|
| 中英文摘要（**申请书必填**） | `nsfc-abstract` |
| 申请代码推荐 | `nsfc-code` |
| 预算说明书 | `nsfc-budget` |

标书配图不在流程内，由你自行完成。

## 六、技术路线怎么写

`nsfc-research-content-writer` 对技术路线有**强制结构要求**，因为"技术路线与研究内容脱节"是这一章最常见的扣分点。

必须写成**总—分两层**：

**（总）总体技术路线** —— 1–2 段 + 技术路线图

- 起点输入是什么
- 主链要经过哪几个关键环节
- **每项研究内容落在主链的哪一环**（"总"与"分"的接缝，必须显式写）
- 环节间是串行依赖还是并行推进
- 整条链跑通后如何达成总目标

把研究内容标题复述一遍**不算**总体路线。

**（分）分项技术路线** —— 每项研究内容一条，五要素齐全

> 输入 → 方法与关键步骤 → 输出 → 验证口径 → 衔接

其中"输入"和"衔接"是把分路线缝回总体路线的针脚。只写"方法+验证"就会退化成方法罗列。

**数量硬约束**：分路线条数 = 研究内容项数，序号严格对应。不允许缺口、孤儿或错位。

**落点随布局变化**：三段式并入研究内容文件；五段式写入独立的 `1.3.方案及可行性`。

完整规范见 [`skills/nsfc-research-content-writer/references/technical_route_structure.md`](../skills/nsfc-research-content-writer/references/technical_route_structure.md)。

## 七、章节编号不能靠猜

NSFC 模板**不共用一套章节编号，而且编号互相重叠**：

| 角色 | 三段式（面上/青年） | 五段式（地区） |
|---|---|---|
| 立项依据 | `1.1.立项依据` | `1.1.立项依据` |
| 研究内容 | `2.1.研究内容` | `1.2.内容目标问题` |
| 方案及可行性 | 无（并入研究内容） | `1.3.方案及可行性` |
| 特色与创新 | `2.2.特色与创新` | `1.4.特色与创新` |
| 年度计划 | `2.3.年度研究计划` | `1.5.研究计划` |
| 研究基础 | `3.1.研究基础` | `2.1.研究基础` |
| 工作条件 | `3.2.工作条件` | `2.2.工作条件` |
| 其他说明 | `4.1`–`4.6` | `3.1`–`3.5` |

注意两处陷阱：

- 五段式的 `2.1` 是**研究基础**，不是研究内容
- 五段式的 `3.1` 是**不同类型国基情况**（声明章节），不是研究基础

所以技能一律**从 `main.tex` 未注释的 `\input{extraTex/...}` 按角色解析**，绝不按编号 glob 选文件。你不需要管这件事，但如果看到 AI 说"落点解析失败，请确认"，原因就在这——它宁可停下来问，也不会猜。

## 八、适用范围

| 项目 | 覆盖 |
|---|---|
| `NSFC_General` / `NSFC_General_Clean`（面上） | ✅ |
| `NSFC_Young`（青年） | ✅ |
| `NSFC_Local` / `NSFC_Local_Clean`（地区） | ✅ |
| `GDNSF_*`（广东省基金） | ❌ 章节体例不同 |
| `GXNSF_*`（广西自然科学基金） | ❌ 章节体例不同 |

省级基金用的是「立**论**依据 / 研究工作基础 / 实验条件 / 项目组人员简介」等另一套章节，`nsfc-full-pipeline` 不覆盖，会显式告知并建议改用单点技能。

**借用模板申报其它类别**（如实验室开放课题）是可以的——沿用 NSFC 章节结构写作，成稿后导入官方表单。但要在项目事实库里写明：

- 需要跳过哪些国基专属章节（完成国基项目情况、各类声明栏）
- 篇幅口径按哪份模板算（**不要**把地区基金的 8000 字上限套到面上项目）

## 九、常见问题

**AI 老是问我已经给过的信息**

多半是三个原因之一：

1. `docs/workflow_status.yaml` 不存在 —— 没有断点，每次都从头跑
2. 事实散在多份文档里，没进事实库，或者没标 `已确认`
3. 同一事实在两份文档里说法不一致，AI 只能停下来问

对策：把事实收敛进两层事实库，冲突的当场裁定并写明口径。

**新项目带着上一个项目的内容**

说明个人材料留在了 `NSFC_*_Clean` 模板里，会随 `create_project.py` 传播。模板的 `docs/` 只应有三个骨架文件（`00_项目事实库.md`、`workflow_status.yaml`、`README.md`）。

**正文写好了但 PDF 没变**

改完 `.tex` 要重新编译：

```bash
python packages/bensz-nsfc/scripts/nsfc_project_tool.py build --project-dir projects/你的项目
```

**想在仓库外写标书**

可以。把项目目录整个移出去，`scripts/nsfc_build.py` 会自动找到已安装的 `bensz-nsfc` 公共包。但共用申请人文件留在仓库里的话，`applicant_profile_file` 的相对路径要相应调整。
