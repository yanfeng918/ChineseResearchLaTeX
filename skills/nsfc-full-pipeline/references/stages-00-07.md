# Stage 00–07：解析、研究设计与正文写作

执行 00–07 任一阶段前必须完整读取本文件。

## Stage 00：布局与项目类型解析

先读项目级 `AGENTS.md`、`README.md` 和 `main.tex`，只解析未注释的 `\input` / `\include`。

必须确定并写入断点：

- `project.type` 与 `project.grant_type`；
- `project.layout`：三段式或五段式；
- `project.length_budget`：取项目级规则；
- `project.body_files.part_one`、`foundation`、`statements`；
- `applicant_profile_file` 与 `project_fact_file`；
- `main.tex` 指纹。

目录名只用于辅助验证，不能覆盖 `main.tex` 的真实引用链。常见布局：

- 三段式：面上、青年；第一部分通常映射 `1.1`、`2.1`、`2.2`、`2.3`；
- 五段式：地区；第一部分通常映射 `1.1`–`1.5`。

若解析结果与已知布局冲突，停下并向用户合并询问，不得猜测。对注释态或孤儿文件只在检查报告记录，不写入。

## Stage 01：选题与研究主题

调用 `research-topic-extractor`，必要时调用 `research-guide-updater`。输出 `docs/01_选题与研究主题.md`，至少包含：

- 研究对象与边界；
- 关键机制、关系或因果链；
- 拟解决的核心科学问题；
- 中英文关键词；
- 可检索的同义词、上位词和方法词。

只有用户材料和项目上下文都无法确定选题时才 `need_user_input`。不要在选题未定时生成整篇内容。

## Stage 02：文献调研

调用 `research-literature-review`，必要时更新研究指南。优先覆盖最近 5 个完整自然年及当前年份的新进展，同时保留必要的奠基文献；不得把固定年份写死。

输出 `docs/02_文献调研/`，并把确认真实、与正文主张匹配的条目写入 `references/myexample.bib`。每个关键论断记录支持文献、反例或争议与项目切入点。

文献闸门按学科适配：

- 所有领域：关键论断有来源，国内外现状、代表性方法、争议与近年进展覆盖充分；
- CS/AI 默认参考：BibTeX 至少 25 条，目标 30–50 条；第一部分正文实际引用约 20–35 条；近 5 年文献比例通常不低于 60%；
- 临床、数学、冷门交叉等领域可按领域证据传统调整数量，但必须在阶段记录中说明理由。

文献不足时继续检索；若受访问限制，生成 `docs/参考文献补充清单.md`，写明待补主题和核验路径，然后继续能安全完成的工作。不得为凑数虚构引用。

## Stage 03：科学问题与创新点

调用 `research-idea`，必要时调用 `research-guide-updater`。输出 `docs/03_科学问题与创新点.md`：

- 一条中心科学问题；
- 2–3 条相互支撑的子问题；
- 可证伪假说或机制判断；
- 创新点及其相对现有工作的差异；
- 证据、风险与边界。

创新必须落到研究对象、机制、方法或可验证关系，不写“首次”“国际领先”等无法证明的宣传句。

## Stage 04：研究方案与技术路线

调用 `research-plan`。输出 `docs/04_研究方案与技术路线.md`，明确：

- 研究目标、内容、方法、指标和预期证据的一一对应；
- 样本/数据、对照、统计或验证方法；
- 技术路线的总—分结构；
- 风险、早期信号、替代路线与降级目标；
- 年度计划和成果口径。

实验规模、阈值、月份和 baseline 若资料不足，可给保守草案并标 `【暂定 …】`，不得把草案写成已确认事实。

## Stage 05：第一部分正文

只写 stage 00 解析出的 `part_one` 文件。按具体章节调用 `nsfc-justification-writer`、`nsfc-research-content-writer` 和 `research-plan`。

正文形成完整闭环：

1. 研究价值与必要性；
2. 国内外现状、进展与不足；
3. 科学问题、假说和项目切入点；
4. 研究目标、内容与关键问题；
5. 方案、可行性、创新与年度计划。

必须使用项目布局对应的文件，不能把三段式编号套到五段式。引用 key 必须存在于 BibTeX 且语义匹配。

## Stage 06：研究基础与工作条件

调用 `nsfc-research-foundation-writer`，只写 stage 00 解析出的 `foundation` 文件。

先读申请人事实与项目事实，再用证据链回答“为什么这个团队能做成”：

- 已有工作如何直接支撑本项目；
- 已具备条件与尚缺条件；
- 团队分工与协作基础；
- 风险及可执行应对。

未知批准号、金额、论文、设备或成员只挖名词短语并使用已登记事实 ID。同步维护一份集中问卷，但不停下等待。

## Stage 07：其他说明

只处理 `statements` 映射中的启用文件。逐项给出真实肯定句或否定句；未知事项使用事实 ID 挖空。不得写注释态的生成式人工智能声明或其他孤儿文件。

输出 `docs/其他说明检查报告.md`，列出：启用声明、禁用声明、待补 ID、事实来源与是否需要用户最终确认。

## 00–07 完成检查

- 当前阶段的输出存在且不是出厂占位；
- 正文句子和论证链完整，硬事实缺口仅限名词短语；
- ID 全部可在事实文件中找到；
- `finish --stage <id>` 成功；
- 有缺口的 05–07 为 `drafted_with_gaps`，不是 `completed` 或 `need_user_input`。
