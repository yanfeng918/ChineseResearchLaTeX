# nsfc-justification-writer 专业性与可读性优化计划

## 通俗解释：究竟发生了什么

- **一句话说明：** 目前 Skill 会检查论证是否成立、引用是否可靠，却没有专门检查一段话是否能让同领域但不做该细分方向的评审顺畅读懂，也没有把这类问题改到更清楚。
- **具体场景：** 评审人熟悉本学科，却未必熟悉申请人使用的每个术语和推理捷径。若一段话把多个限定条件、缩写和结论挤进一个长句，评审即使认可研究主题，也要反复拆解句子才能判断论证；这会削弱立项依据的说服效率。
- **对应到本问题：** “不顺畅”不是把专业内容改成科普，而是让每段的主张、证据、缺口和项目切入点可以被大同行准确、低负担地追踪；专业术语、必要的限定和学术严谨性仍应保留。
- **改变前后：** 现在的输出可能只指出“逻辑跳跃”或“证据不足”。改进后，Skill 会单列可读性复核：指出具体的表达障碍、说明为什么会影响大同行理解，并给出不改变事实、术语边界和 LaTeX 结构的替换建议。

## 专业判断：问题在哪里

- **当前现象：** `SKILL.md` 的推荐工作流覆盖论证闭环、术语一致性和引用核验；`review_suggestions.txt`、`writing_coach.txt` 与 `tier2_diagnostic.txt`也主要围绕这些维度。它们没有要求模型系统识别过度嵌套的长句、指代不清、缩写未铺垫、名词堆叠、主谓关系不明或连接关系缺失等阅读障碍。
- **已有基础：** `scripts/core/review_advice.py` 已能通过 `review` 输出“评审人问题 + 可执行建议”，并在 AI 不可用时提供稳定的回退建议；`scripts/core/writing_coach.py` 已有 `polish` 阶段。因此无需新建独立 CLI，也不必把主观写作质量硬编码成通过/拒写门槛。
- **影响范围：** 只影响 Skill 的语义审查与润色建议，不改变引用守护、preview/diff、写入确认、备份/回滚等安全边界；不修改用户的标书正文。
- **已知风险：** 单纯追求短句或“通俗”会损失限定条件、误改术语，甚至把学术推理稀释成宣传语。因此检查必须以“准确优先、减轻理解负担”为原则，输出建议而非自动判定不合格。

## 要达到什么目标

- **完成后的变化：**
  - 每次完整审查都把“专业性—可读性平衡”作为与逻辑、证据并列的人工判断维度。
  - 对发现的问题给出可定位、可修改的建议：问题属于什么类型、为什么妨碍大同行理解、怎样改写且不改变原意。
  - `polish` 阶段会先完成事实与逻辑守护，再进行可读性精修；改写仍保留专业术语、证据边界、引用命令与现有 LaTeX 结构。
  - AI 不可用时，`review` 仍能提出简短、可操作的可读性自检问题和修改方向。
- **不在本次处理范围：**
  - 不引入句长、被动语态比例、术语数量等机械分数，也不以这些指标阻止写入。
  - 不把立项依据降格为科普文，不要求删除必要的专业术语、条件、引文或不确定性表述。
  - 不增加新的自动写入命令、外部模型依赖或网页报告。
  - 不与现有的“精简重构计划”重复处理固定标题、文件名与旧 CLI 的迁移；仅确保本项改动可叠加于该计划的语义优先方向。

## 改进方向

### 建立面向大同行的可读性判断准则

在 `references/` 新增一份短小的写作准则，并在 `SKILL.md` 的语义写作规则和推荐工作流中引入。准则应要求模型从评审阅读体验出发，检查并优先处理以下情形：

- 单句承载过多并列动作、限定条件或因果层级，导致主张与依据难以辨认；
- “这/其/该机制”等指代对象不明确，或新概念、缩写在首次出现时没有可理解的界定；
- 多个抽象名词连续堆叠，却未说明它们之间的关系或可观察含义；
- 段内缺少“已有事实—尚存缺口—本段结论”的必要衔接，使读者只能自行补全推理；
- 为显得专业而使用生僻、空泛或过度修饰的表述，但其不增加准确性。

每条都应同时明确保护边界：保留已核验事实、研究对象、必要限定、科学问题/假设的精确形式和 LaTeX 命令；无法在不改变科学含义的前提下改写时，只说明风险并向用户询问。对使用者而言，这意味着建议会更像一次熟悉本领域的同行审稿，而非按语法模板“削句子”。

### 将可读性复核嵌入既有审查与润色链路

调整 `assets/prompts/review_suggestions.txt` 和 `assets/prompts/writing_coach.txt`：

- `review` 输出除逻辑闭环、证据与术语问题外，增加“专业可读性”问题及对应修改建议；每条建议应说明位置或可辨识的原句特征、阅读障碍类型、保留的科学含义和推荐改法。
- `coach --stage polish` 明确采用“两步润色”：先确认论证、事实和引用未被改变，再按段拆开冗长句、补足指代和过渡、在首次出现处简要界定必要术语；不以删除术语或盲目缩短字数作为目标。
- `tier2_diagnostic.txt` 的 JSON 契约可增设独立的 `readability` 列表，或在保持兼容前提下将此类发现纳入 `suggestions`。实现时优先选可向后兼容的字段扩展，并同步聚合与展示逻辑，避免丢弃 AI 返回的可读性发现。

对普通使用者而言，`review` 可以直接回答“哪里让评审读起来费力、怎样改得清楚”；`coach` 则在真正润色时把这些建议落实为受约束的正文改写。

### 补足无 AI 回退与交互文案

更新 `scripts/core/review_advice.py` 的 `_fallback_review_markdown()`：加入少量可读性复核问题和相应的行动建议，例如检查每段能否用一句话说清主张、每个首次出现的缩写是否有解释、长句能否在不损失限定条件时拆成“事实/转折/结论”两到三句。

同时调整 `scripts/core/writing_coach.py` 中 `polish` 阶段的回退任务和可复制提示词，使无 AI 或提示词加载失败时仍维持同一原则。这里不应新增硬失败状态，也不应恢复已被精简重构计划降级的固定小标题或四维度要求。这样无论是否接入 AI，用户都能获得一致的审查方向。

### 保持输出契约与文档一致

更新 `SKILL.md` 的“语义写作规则”“推荐工作流”和“输出契约”，要求在完成逻辑、术语与引用检查后进行一次专业可读性复核，并将发现归为“表达建议”，而非事实错误或写入阻断条件。

同步维护 `README.md` 的“它会检查什么”和常见问题，明确该能力面向大同行阅读、不会把专业内容简单化。按项目 Skill 规范更新 `config.yaml` 版本、Skill 级 `CHANGELOG.md`、根级 `CHANGELOG.md`；教程和工作流优先直接合并到 README，避免重复的文档索引层。这样用户看到的能力、执行规则和版本记录保持一致。

### 用对照样例验证“清楚而不失真”

在现有 `evals/evals.json` 基础上增加至少三类真实写作提示，并保留原有结构/安全用例：

1. 一段术语正确但句子嵌套、名词堆叠的立项依据；期望指出具体阅读障碍，并给出保留术语和限定条件的改写。
2. 一段缩写、指代或机制关系不清的文字；期望补足首次界定和衔接，而不杜撰背景事实或引用。
3. 一段本已简洁但包含必要专业条件与可证伪假设的文字；期望确认其可读性良好，避免为“通俗”而删减科学精度。

为脚本回退输出补充针对 `review` / `coach polish` 的定向测试；若现有测试框架尚未覆盖这些函数，先以最小单元测试固定关键问句与“仅建议、不拒写”的行为。评测应比较修改前后是否更易识别主张、证据和缺口，同时确认引用、事实、结构命令和用户授权范围没有变化。

## 实施范围与顺序

1. 先定义并确认“专业可读性”的判断准则和保护边界，避免把润色误做成去专业化。
2. 将准则写入 `SKILL.md`、AI 审查/教练提示词和 `polish` 的输出要求，使人工调用与脚本辅助遵循同一标准。
3. 更新 `review_advice.py`、`writing_coach.py` 的无 AI 回退内容；若 Tier2 增加字段，同时完成聚合、展示与兼容处理。
4. 添加正反对照评测和定向测试，验证“发现并优化阅读障碍”与“保护科学准确性”同时成立。
5. 最后同步 README、参考文档索引、版本号与两级变更日志，并运行现有配置校验和相关测试。

## 如何确认完成

- 用户要求审查或润色时，Skill 会在逻辑、术语、引用之后明确执行专业可读性复核。
- 输出能说明至少一个可读性问题的类型、位置/原句特征、影响和保真改法，而非泛泛地说“语言不够流畅”。
- 面对合格的专业表述，Skill 不会仅因术语密度或句子较长而强行改写。
- 面对含有复杂但必要限定的科学问题或假设，改写后仍保持原有对象、条件、可证伪性、引用命令和 LaTeX 结构。
- AI 不可用时，`review` 与 `coach --stage polish` 仍给出一致的可读性检查和建议，且不把此类问题作为拒写条件。
- 原有自定义文件名/标题、preview/diff、引用核验与写入确认评测继续通过；新增三类可读性样例均达到预期。
- `config.yaml`、`SKILL.md`、README、参考索引与 CHANGELOG 的能力描述和版本号一致。

## 风险与待确认事项

- **主观性：** 可读性无法由单一数值可靠衡量。计划采用“具体问题 + 可保真改写”的审稿式输出，并保留用户对语气和术语的最终判断。
- **术语损失：** 改写必须保留必要术语；首次界定可以用短语补足，不把专业概念替换成不精确的日常词。
- **兼容性：** 如果为 Tier2 新增 `readability` 字段，需要让旧缓存、旧 responder 和现有 JSON 消费路径在该字段缺失时正常工作。
- **现有未提交改动：** 该 Skill 当前已有精简重构相关的工作区改动。实施时应在这些改动之上最小追加，不覆盖或回退任何未提交文件。
